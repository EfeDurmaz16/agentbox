## Problem Statement

Autonomous AI agents (OpenClaw, Hermes, Perplexity Personal Computer) run 24/7 on personal machines. People are so afraid of destructive actions that they buy dedicated Mac Minis ($599) as physical isolation. Apple stores run out of stock. Meanwhile, the YOLO majority runs agents with full machine access and zero governance.

Every existing agent governance product (Microsoft Agent Governance Toolkit, Agent Action Firewall, NVIDIA NemoClaw, Palo Alto Prisma AIRS) targets enterprises with SDK integrations and cloud infrastructure. Zero products target the individual developer or creator running an autonomous agent on their personal computer.

The gap: a software layer that replaces the $599 Mac Mini with a daemon that lets agents run free for safe actions and intercepts dangerous ones with a phone approval gate. Like 2FA for agent actions.

## Demand Evidence

- **Market signal:** OpenClaw's viral adoption drove Mac Mini shortages at Apple stores globally. CNBC reported secondhand MacBook prices rising in China due to OpenClaw demand. Tech market firm Omdia estimated Mac Mini shipments grew double digits YoY. People are spending $599 on physical isolation because no software alternative exists.
- **Status quo split:** Two camps. Mac Mini buyers (expensive, growing) and YOLO (free, vast majority). Almost nobody doing systematic manual guardrails. The absence of a middle option is the opportunity.
- **Enterprise validation:** Microsoft, Palo Alto, IBM, NVIDIA all launched agent governance products in Q1 2026. The category is validated. They just built it for the wrong customer.

## Target User and Narrowest Wedge

**Target user:** Individual developer or creator running OpenClaw, Hermes, or Claude Code on their Mac. Not an enterprise. Not a security team. Someone who wants their agent to code freely but doesn't want it to `rm -rf ~/Documents` or `git push --force` to production at 3am.

**Wedge:** A macOS daemon that intercepts dangerous commands and sends a push notification to your phone. You tap Approve or Deny. Agent continues or stops. That's it.

Three buckets, strong defaults, zero config:
- **Allow:** read files, write code, run tests, install deps in workspace
- **Approve:** delete outside workspace, DB writes, network egress to domains not in user allowlist (default: empty, so all external domains require approval on first use; "Always allow" adds to allowlist), send email/messages, credential access (reads from `~/.ssh/`, `~/.aws/`, `~/.config/gcloud/`, `*.env` files, macOS Keychain API), git push, remote shell
- **Block:** rm -rf /, delete ~, wipe disks, format volumes

## Constraints

- Must work without agent-specific SDK integrations (universal interception)
- Must be installable via `brew install` with zero config
- Must have negligible overhead for allowed actions (target <50ms pass-through for shims, sub-ms for ES framework; shims use pre-forked daemon socket to avoid cold-start per invocation)
- macOS first (where Mac Mini buyers are), Linux second
- Phone notification approval must work when user is away from computer
- Local-first: policy engine and audit log are fully local. Push notification delivery is an explicit external dependency (ntfy self-hosted satisfies strict local-first; Pushover/ntfy.sh cloud are acceptable defaults)
- Single developer building this (founder is the engineer)

## Approaches Considered

### Approach A: PATH Shim Daemon (v0.1 — ship in 2 weeks)

Rust daemon + compiled shim binaries for dangerous commands. Shims sit first in PATH. Agent calls `rm`, hits shim, shim checks policy and sends phone notification.

- Effort: M (2-3 weeks)
- Risk: Low
- Pros: Works with any terminal agent, zero config, <50ms overhead via daemon socket, single binary install
- Cons: Only intercepts shell commands, bypassable via full paths (/bin/rm) or direct syscalls

### Approach B: Endpoint Security Agent (v1 — ship in 6 weeks)

macOS Endpoint Security framework to intercept ALL process exec, file unlink, network connect at kernel level. Cannot be bypassed. Same mechanism as CrowdStrike/SentinelOne.

- Effort: L (4-6 weeks, requires Apple Developer cert)
- Risk: Medium (ES framework is complex, requires System Extension approval)
- Pros: True universal interception, cannot be bypassed, fulfills premise #4
- Cons: macOS only, requires $99/yr Apple Developer Program, harder to develop

### Approach C: MCP Governance Proxy (v1.5 — adds protocol-level context)

Local MCP proxy between agent and MCP servers. Intercepts tool calls with full semantic context. Richer approval messages ("Agent wants to call supabase.delete_table('users')").

- Effort: M (3-4 weeks)
- Risk: Medium (depends on MCP adoption)
- Pros: Protocol-level context, cross-platform, richer risk classification
- Cons: Only catches MCP calls natively, needs PATH shim fallback

## Recommended Approach

**All three, phased: A then B then C.**

| Phase | Timeline | What ships | Interception |
|-------|----------|-----------|-------------|
| v0.1 | Week 2 | PATH shim daemon + phone approval | Shell commands |
| v1.0 | Week 6 | Endpoint Security agent | ALL process/file/network |
| v1.5 | Week 10 | MCP proxy layer | Tool-level semantic context |

Each phase ships independently. Each phase makes the product strictly better. Users see the same UX throughout; the enforcement mechanism strengthens underneath.

## Approval Timeout Policy

When a phone notification is sent and the user does not respond:
- **Default:** Auto-deny after 120 seconds. The agent receives a "denied" response and can retry or proceed differently.
- **Configurable:** User can set timeout to 30s-600s, or "block indefinitely" (agent waits forever until response).
- **Blocked actions (bucket 3):** No timeout; these are always denied instantly, no notification sent.

## Audit Log Schema

Append-only SQLite table, one row per intercepted action:

| Field | Type | Description |
|-------|------|-------------|
| `id` | TEXT | ULID |
| `timestamp` | TEXT | ISO 8601 UTC |
| `agent_pid` | INTEGER | PID of the process that invoked the command |
| `agent_name` | TEXT | Best-effort detection (e.g., "openclaw", "claude-code", "unknown") |
| `command` | TEXT | Full command line intercepted |
| `cwd` | TEXT | Working directory at invocation |
| `bucket` | TEXT | "allow", "approve", or "block" |
| `decision` | TEXT | "allowed", "approved", "denied", "blocked", "timed_out" |
| `user_response_ms` | INTEGER | NULL for allow/block; ms until user tapped for approve |
| `parent_process` | TEXT | Parent process name/path |

Storage: `~/.agentbox/audit.db`, rotated monthly, exportable as JSONL.

## The Assignment

**Do not build v0.1 yet.** First, do this:

1. Open 3 terminals. Run OpenClaw in terminal 1, Hermes in terminal 2, Claude Code in terminal 3. Give each a task that involves destructive operations (delete files, git push, run SQL).
2. Watch what commands they actually execute. Log every shell command. This is your ground truth for what the shims need to intercept.
3. Count: how many unique commands would need shims? How many are safe? What's the ratio?
4. If the dangerous commands are fewer than 20 distinct binaries, PATH shims are viable. If they're 50+, you need Endpoint Security from day 1.

This takes 2 hours. Do it before writing a line of code. Your entire risk classification model depends on empirical data about how these agents actually behave in the wild.
